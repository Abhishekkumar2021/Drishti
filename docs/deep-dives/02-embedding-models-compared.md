## 1. Why Building Drishti Is Hard

Vector search is not a one-size-fits-all solution. For natural language, semantic dense search is ideal. But when searching code repositories, queries contain exact keywords and unique terms:

* **Keyword Queries**: If a developer searches for the variable name `jwt_secret`, they want the exact line defining that variable. Dense vector similarity search often misses these exact matches, returning conceptually related code (like general crypto hashing methods) instead.
* **Semantic Queries**: If a developer asks "Where is the database connections timeout handled?", they are looking for the concept of timeouts. Sparse keyword search (BM25) fails here if the exact words "database", "connections", or "timeout" are not in the code.

To solve this, Drishti implements a **hybrid search** system that stores both dense and sparse representations of chunks in a single collection.

## 2. Core Theory: Vector Spaces & Inner Products

Retrieval-augmented generation uses vector spaces to map semantic meanings.

### A. Vector Embeddings
An embedding maps text to a high-dimensional vector space where the distance between points reflects semantic similarity.

### B. Similarity Metrics
To compare vectors, we calculate the angle between them using **Cosine Similarity**:

$$\text{Cosine Similarity}(\mathbf{u}, \mathbf{v}) = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\| \|\mathbf{v}\|} = \frac{\sum u_i v_i}{\sqrt{\sum u_i^2} \sqrt{\sum v_i^2}}$$

If the vectors are normalized ($\|\mathbf{u}\| = 1$), Cosine Similarity simplifies to the **Dot Product** ($\mathbf{u} \cdot \mathbf{v}$), which is faster to compute.

## 3. Dense vs. Sparse Vectors

Drishti uses both vector representations to capture different search signals:

| Attribute | Dense Vectors | Sparse Vectors |
|-----------|---------------|----------------|
| **Dimensionality** | Fixed, continuous float dimensions (e.g. 1536). | Very high, discrete dimensions (vocabulary size). |
| **Value Density** | Every dimension contains a non-zero float. | Most dimensions are zero; only matching terms have values. |
| **Strengths** | Captures synonyms, concepts, and semantic intent. | Captures exact class names, variable codes, and keywords. |
| **Model Source** | Configurable via `EMBEDDING_PROVIDER` (OpenAI, Cohere, Ollama, OpenAI-compatible). | BM25 (in-process). |

---

## 4. Embedding Models: Dimension vs. Context Trade-offs

Choosing the right dense embedding model involves balancing quality, cost, and latency:

* **`text-embedding-3-small` (1536 dims)**: Offers high semantic recall on code and lower API token costs compared to larger models.
* **`text-embedding-3-large` (3072 dims)**: Highly accurate, but doubles vector database memory requirements and search latency.
* **Local Models (e.g. `BGE-large` / `Instructor`)**: Avoid external API dependencies but require local GPU resources to match cloud API throughput.

## 5. Drishti's Hybrid Storage Setup

We configure Qdrant to store both vector spaces in a single point payload:
* **Dense Named Vector**: Stores 1536 float values generated by OpenAI.
* **Sparse Named Vector**: Stores token frequency indices and weights.

During queries, both vector spaces are searched, and the results are combined.

## 6. How Senior Interviewers Test This

**"Why do you need both dense and sparse vectors? Can't we just tune the dense model?"**
> Dense vectors map semantic meaning, while sparse vectors map keyword frequencies. In codebase searches, developers often search for exact variable names, hashes, or API paths (e.g., `/api/v1/users`). Dense models are not optimized for exact string matches and can fail to retrieve these points. Storing both allows us to merge their search signals.

**"What is the mathematical advantage of using Cosine Similarity over L2 (Euclidean) distance?"**
> L2 distance measures the straight-line distance between two vector points. It is sensitive to document length; a long document containing the same terms repeated will have a larger L2 distance from a short query. Cosine similarity measures the angle between the vectors, normalizing for document length and focusing on semantic orientation.

## 7. Key Takeaways & What's Next

1. **Semantic queries require dense vectors**, while **exact keyword searches require sparse vectors**.
2. **Cosine similarity measures vector angle**, normalizing for document length.
3. **Drishti uses named vectors in Qdrant** to store both dense and sparse representations.
